Every line is a real FOREIGN KEY constraint, enforced by Azure SQL — 11 in total. The old supplier_invoices_head ↔ supplier_invoices_detail link used to be business-key-only, since Invoice_Number is intentionally non-unique (duplicate invoices on the head side, bundled lines on the detail side) and a FOREIGN KEY must reference a PRIMARY KEY/UNIQUE column. The 2026-08-20 rebuild replaced that link with a system-generated Voucher_Number — the same thing a real AP system uses as its true primary key, with Invoice_Number demoted to a descriptive field that's still deliberately non-unique (that's what makes the DUPLICATE_INVOICE fraud case realistic: the same vendor invoice number entered twice, as two different vouchers).

Review

Judgment calls baked into this diagram

Type

GST_Registered (vendor_master) and memo (purchase_orders) are the only two True/False-shaped columns in this schema — both stored as genuine BIT, matching what the source generator actually produces. GST_Registered was originally documented as NVARCHAR(10) text; memo was missing from the schema doc entirely. Both corrected 2026-08-20.

Foreign keys

All 11 relationships above are real, enforced FOREIGN KEY constraints — this is a reporting/warehouse extract rather than a live OLTP system, but every one of these holds reliably in every row, so they're worth enforcing rather than leaving as documentation only. The SKU_ID FK only works because Purchasing.py writes a placeholder SKU_ID = "GENERAL" row into sku_master for memo lines — the standard "unknown/not-applicable member" pattern for a dimension table, kept out of the random sampling pool used for genuine catalog lines.

Key design

No table in this schema has a SQL-generated IDENTITY key. Every primary key is a natural business key — including supplier_invoices_head (Voucher_Number) and supplier_invoices_detail (Invoice_Line_ID), both generated in Purchasing.py rather than by SQL Server at load time, so the same ID is stable across CSV, SQL, and Power BI. Two tables use a natural composite key: vendor_bank_accounts (Vendor_ID + Effective_Start_Date) and goods_receipt_applications (Invoice_Line_ID + Receipt_ID).

Full P2P rebuild

2026-08-20: went from 6 tables to 10, adding vendor_bank_accounts, goods_receipt_applications, payment_batches, and payments. The prior model stopped at "invoice references a PO line" — this rebuild added the actual receipt-to-invoice matching record, so three-way-match exceptions (unreceived invoices, over-invoiced quantities, duplicate-invoice claims against the same receipt) are derivable facts rather than a synthetic label; and a full payment layer with an effective-dated vendor bank-account history, so a payment sent to an account never valid for that vendor, or valid once but since superseded, is a detectable fraud signature rather than untestable. Azure SQL was fully dropped and recreated against the new schema; the Power BI semantic model was rebuilt table by table and verified refresh-clean with row counts matching Azure SQL exactly throughout.

Renamed & extended

purchase_orders_au_chaos renamed to purchase_orders throughout (table, CSV, scripts, Power BI). sku_master gained Days_To_Deliver (agreed lead time in days) and purchase_orders gained Expected_Delivery_Date (Date + Days_To_Deliver) — together these support a real DIFOT "on time" measure, not just "in full."
